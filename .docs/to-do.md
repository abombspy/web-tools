# 향후 추가 고려 기능 (아이디어 백로그)

아직 사용자 요청·승인을 받지 않은 **아이디어 목록**이다. `.docs/plan.md` §6의 항목들과
달리 리스크 추적이 아니라 "다음에 뭘 더 할 만한가"를 정리한 백로그이므로, 실제로
진행하려면 각 항목마다 범위와 방식을 사용자와 다시 확인해야 한다. 이 사이트는 서버·DB가
없는 순수 정적 내보내기(클라이언트 계산만, 입력값 저장 안 함)라는 제약을 유지하는 방향의
아이디어 위주로 정리했다.

작성일: 2026-09-23

---

## 0. 검색엔진 소유권 확인·sitemap 등록 진행 상황 (2026-09-23)

아이디어가 아니라 실제로 진행 중인 작업이라 별도로 기록한다. §4의 "Google Search Console/
네이버 서치어드바이저 등록"은 아래 내용으로 갱신됨.

- ✅ 구글 서치 콘솔 소유권 확인 메타태그 추가(`<meta name="google-site-verification">`,
  `src/app/layout.tsx`의 `metadata.verification.google`) — 속성은 URL 접두어
  `https://abombspy.github.io/web-tools/`로 등록.
- ✅ 네이버 서치어드바이저 소유권 확인 메타태그 추가(`<meta name="naver-site-verification">`,
  `metadata.verification.other`) — 네이버는 호스트(도메인) 단위 확인이라, `web-tools`
  저장소뿐 아니라 루트 도메인(`https://abombspy.github.io/`)을 서비스하는 별도 저장소
  (`abombspy/abombspy.github.io`)의 `index.html`에도 동일한 메타태그를 추가함.
- ✅ `SITE_URL`(`src/lib/site-config.ts`)이 아직 연결 전인 커스텀 도메인
  (`web-tools.gssystems.co.kr`)을 가리키고 있던 걸 실제 배포 주소
  (`https://abombspy.github.io/web-tools`)로 수정 — sitemap.xml/robots.txt/OG url/
  JSON-LD가 전부 이 값을 참조하므로 한 곳만 고치면 전체 반영됨. 이 수정 전에는
  sitemap.xml이 위치한 도메인과 그 안의 `<loc>` URL 도메인이 서로 달라(구글 sitemap
  규격 위반) 구글이 "sitemap을 찾을 수 없음"으로 표시했을 가능성이 있음 — 지금은 해소됨.
- ⬜ **사용자가 직접 해야 하는 남은 절차** (로그인 필요해서 대행 불가):
  - 구글 서치 콘솔에서 "확인" 버튼 클릭.
  - 네이버 서치어드바이저에서 "확인" 버튼 클릭.
  - 구글 서치 콘솔의 Sitemaps 메뉴에서 기존 `sitemap.xml` 제출 항목을 삭제 후 재제출
    (SITE_URL 수정 전 상태가 캐시돼 있을 수 있어, 삭제·재제출로 재크롤링 유도 권장).
  - 네이버 서치어드바이저에도 sitemap 제출(`https://abombspy.github.io/web-tools/sitemap.xml`).
  - 재제출 후에도 상태 갱신까지 수 시간~1~2일 걸릴 수 있음(정상적인 지연이며 문제 아님).
- 나중에 커스텀 도메인(`web-tools.gssystems.co.kr`)을 실제로 연결하면: (1) `SITE_URL`을
  그 도메인으로 다시 변경, (2) 구글·네이버 양쪽에 새 도메인 속성을 추가해 재확인, (3) 루트
  저장소(`abombspy.github.io`)는 그때부터 커스텀 도메인이 자체 루트를 가지므로 소유권
  확인 메타태그 유지 여부를 다시 판단해야 함.

## 1. 방금 만든 공유 기능과 바로 이어지는 것

- **입력값을 URL 쿼리 파라미터에 담아 공유**: 지금 공유 버튼은 현재 페이지 URL만 공유하므로,
  상대방은 직접 값을 다시 입력해야 결과를 재현할 수 있다. 시급·생년월일 같은 입력값을
  쿼리 파라미터로 인코딩해 공유하면, 링크를 받은 사람이 동일한 계산 결과를 바로 볼 수
  있다(예: 카카오톡으로 "이번 달 내 주휴수당" 링크를 보내면 상대도 같은 화면을 봄). 서버
  저장이 필요 없어 지금 아키텍처와 잘 맞는다.
- **계산 결과 공유 카드(동적 OG 이미지)**: plan.md §6.15에서 "43개 도구 페이지별 OG
  커스터마이징은 안 함(스코프 축소)"이라고 정리했는데, 이건 페이지 자체가 아니라
  **계산 결과값**을 담은 카드 이미지를 그때그때 만드는 것이라 성격이 다르다. `next/og`
  (이미 대표 이미지 생성에 쓰고 있음)로 "MBTI 결과는 ENTP", "예상 실업급여 150만원" 같은
  결과를 담은 이미지를 만들어 카카오톡/SNS 공유 시 노출되게 하면 클릭률에 도움이 될 수 있다.

## 2. 재방문·개인화 (서버 없이 localStorage만으로)

- **자주 쓰는 계산기 즐겨찾기**: 홈 상단에 "즐겨찾기" 섹션을 두고 localStorage에 저장 —
  계정 없이도 개인화 가능.
- **최근 입력값 자동 채움**: 같은 계산기를 재방문했을 때 지난번 입력값을 localStorage에서
  불러와 미리 채워주는 정도(서버 저장 없음, 자동완성 수준).
- **다크모드 수동 토글**: 지금은 `prefers-color-scheme`(시스템 설정)만 따르는 것으로 보임 —
  헤더에 명시적 토글 버튼을 추가하면 시스템 설정과 무관하게 선택 가능.

## 3. 계산기 자체의 기능 확장

- **시나리오 비교**: 예를 들어 "시급 A vs 시급 B", "지금 퇴사 vs 한 달 뒤 퇴사"처럼 입력
  두 세트를 나란히 비교해 보여주는 모드. 알바·직장인, 생활·주거 카테고리 계산기들과
  특히 잘 맞는다(이미 있는 퇴사 시점 비교 계산기가 이 패턴의 선례).
- **계산 결과 PDF/이미지 다운로드**: 실업급여·육아휴직급여처럼 제출·보관용으로 결과를
  캡처해두고 싶은 계산기에 유용. 브라우저 내에서 처리 가능(서버 불필요, `text-file` 카테고리의
  기존 클라이언트 처리 패턴 재사용 가능).
- **관련 도구 추천 고도화**: 지금은 페이지 하단에 정적인 "함께 보면 좋은 계산기" 링크만
  있음(plan.md §7.1) — 계산 결과에 따라 동적으로 다음 도구를 추천(예: 주휴수당 계산 후
  "이 급여로 종합소득세도 확인해 보세요")하면 체류시간·페이지뷰 증가에 도움이 될 수 있음
  (plan.md §6.10의 SEO topical authority 전략과도 연결됨).

## 4. 트래픽/SEO — 이미 plan.md §6에 추적 중인 미완료 항목 (재강조)

새 아이디어는 아니고, plan.md §6에 이미 있는 미완료(⬜) 항목 중 비용·리스크 대비 효과가
큰 것들을 상기시키는 목적으로 다시 짚어둔다:

- Google Search Console 등록(§6.14) — sitemap.xml은 이미 준비돼 있어 등록만 하면 됨.
- 네이버 서치어드바이저 등록(§6.10, §6.14, §6.15) — 한국 검색 트래픽 비중이 커서 우선순위 높음.
- 애드센스 광고 단위 실제 삽입(§6.2) — 심사 통과 후 TODO 자리(43개 페이지)에 코드 삽입 필요.

## 5. 추가할 만한 콘텐츠 (신규 계산기 · 문서형 콘텐츠)

기능이 아니라 **콘텐츠(새 계산기, 새 글)** 관점의 백로그. requirement.md에 명시된 7개
카테고리 43종 이후 후보들이며, 실제로 만들려면 §6.3(정확성 검증)·§6.7(무자격 상담 오인
리스크)과 동일한 검증 절차를 거쳐야 한다.

### 5.1 신규 계산기 후보 (카테고리별)

- **알바·직장인**: **연봉 실수령액 계산기**(연봉 입력 → 4대보험·소득세 반영한 월 실수령액,
  한국에서 검색량이 매우 높은 키워드인데 현재 목록엔 없음) · 퇴직금 단독 계산기(지금은
  "퇴사 시점 비교"에 곁들여져 있고 단독 계산기는 없음) · 야간·연장근로수당 단독 계산기.
- **프리랜서·사업자**: 간이과세자 vs 일반과세자 부가세 비교 · 지역가입자 건강보험료 예상
  계산기(직장가입자와 달리 소득·재산 기준이라 프리랜서 전환 시 충격이 큼, 수요 있을 것으로
  예상).
- **생활·주거**: **취득세 계산기**(부동산 매매 시 검색량 높음) · 자동차세 계산기 ·
  재산세 계산기.
- **육아·건강**: 임신 주수 계산기(마지막 생리일 기준 "지금 몇 주"—출산 예정일 계산기와
  다른 수요).
- **학생·수험생**: 학자금 대출 상환 계산기.
- **재미·바이럴**: **로또 번호 생성기**(트래픽 유입 목적으로 검색량이 매우 높음, 법적
  리스크도 낮음).

우선순위를 매긴다면 검색량·법적 리스크 낮음 기준으로 연봉 실수령액 계산기·취득세
계산기·로또 번호 생성기가 먼저 검토할 만하다.

### 5.2 문서형 콘텐츠(계산기가 아닌 글)

- **카테고리 허브 가이드 글**: 예) "2026년 최저임금 총정리", "알바생이 꼭 알아야 할
  노동법 5가지" 같은 長文 가이드를 카테고리 랜딩 페이지에 추가하고, 관련 계산기로
  내부링크 — plan.md §6.10의 롱테일 키워드·topical authority 전략을 실제 콘텐츠로
  구현하는 것.
- **용어집(글로서리) 페이지**: 계산기 전반에서 반복되는 세금·노동법 용어(소정근로시간,
  경비율, 원천징수 등)를 한곳에 모아 설명하고, 각 계산기 설명 본문에서 링크 — 내부링크
  허브 역할 + 체류시간 증가.
- **각 도구 페이지에 FAQ 섹션**: 지금은 계산 원리 설명(prose)만 있는데, 자주 묻는 질문
  (예: "주휴수당은 지각해도 나오나요?")을 Q&A 형식으로 추가하면 구글의 FAQ 리치 스니펫
  대상이 될 수 있음(§6.15의 SNS 메타데이터와는 별개로, 검색 결과 자체의 노출 면적을
  키우는 효과).

## 6. 스코프 밖 후보 (참고용, 지금 우선순위 아님)

- **PWA(홈 화면 추가·오프라인 지원)**: 계산기가 전부 클라이언트 전용이라 기술적으로는
  적합하지만, 정적 내보내기 배포 파이프라인에 서비스워커·매니페스트를 더하는 작업이라
  별도 검토 필요.
- **제3의 언어(중국어·베트남어 등) 추가**: 외국인 근로자 비중을 고려하면 후보가 될 수
  있으나, 영문판(plan.md §9.3)만큼의 법령 번역 정확도 리스크를 다시 감수해야 해서 신중한
  접근 필요.
- **피드백 위젯(도움이 됐어요/아니요)**: 서버 없이 GA4 이벤트로만 집계하는 정도라면 가능하나,
  악용(어뷰징) 방지·집계 UI 설계가 추가로 필요.
