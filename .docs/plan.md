# 웹 기반 생활/세금/급여 도구 서비스 개발 계획

> `requirement.md` 기반으로 작성. 각 메뉴(카테고리)와 서브 메뉴(개별 계산기)에 대해
> **왜 만드는지(수요/사업 근거)** 와 **어떻게 계산하는지(법령·공식 근거)** 를 정리하고,
> 이를 바탕으로 한 공통 아키텍처와 개발 순서를 정의한다.

---

## 1. 서비스 개요

- 웹 기반 무료 계산/변환 도구 모음 + 애드센스 광고 수익 모델
- 사용자 입력값으로 즉시 계산/표시만 하며, **서버에 데이터 저장하지 않음** (개인정보/보안 이슈 최소화, 백엔드 최소화)
- 세금·급여처럼 **매년 바뀌는 값(요율, 최저임금, 상한액 등)은 코드에 하드코딩하지 않고 설정 파일로 분리**
- 계산기마다 상단에 "이 계산이 어떤 원리/법적 근거로 이루어지는지"를 설명하는 섹션을 두어
  신뢰도 확보 + 체류시간 증가(SEO/광고 노출에 유리) + E-E-A-T(전문성/신뢰성) 확보

---

## 2. 공통 아키텍처 원칙

### 2.1 요율/기준값의 설정 파일화
- 매년 바뀌는 값(최저임금, 실업급여 상하한액, 부가세율, 근로소득 간이세율표, 전기요금표, 관세 면세한도 등)은
  **도메인별로 분리한 설정 파일**(`config/rates/labor.json`, `config/rates/tax.json` 등, 파일 내부는 연도를 키로 관리)로 분리한다.
  구체적인 스키마와 결정 근거는 §7.2 참고.
- 코드는 "설정값을 읽어 계산하는 순수 함수"로만 구성 → 매년 개정 시 배포 없이(또는 설정 파일 교체만으로) 대응 가능
- 연도 전환기(1월)에는 사용자가 연도를 선택할 수 있게 하여 과거/신규 기준 비교 가능

### 2.2 무저장 원칙
- 입력값은 클라이언트(브라우저) 상태로만 유지, API 호출 없이 클라이언트 계산 우선(순수 JS 로직)
- 서버가 필요한 경우(예: 공휴일 데이터 조회)에도 로그에 사용자 식별정보 남기지 않음

### 2.3 페이지 공통 구조
1. **설명 영역(상단)**: 계산 원리, 관련 법령/공식, 용어 설명, 예시
2. **입력 영역**: 최소 입력값 + 툴팁으로 오해 방지
3. **결과 영역**: 계산 결과 + 계산 과정(중간값) 공개 → 신뢰도 확보
4. **광고 영역**: 설명 영역과 결과 영역 사이, 결과 하단 등 콘텐츠 밀도가 높은 지점에 애드센스 슬롯 배치(정책 준수: 콘텐츠 대비 과도한 광고 배치 금지)
5. **관련 도구 추천**: 동일 카테고리 내 다른 계산기로 연결(체류시간·페이지뷰 증가)
6. **반응형 레이아웃**: 대메뉴 8개·서브메뉴 다수를 담는 내비게이션은 데스크톱 메가메뉴/모바일 아코디언으로 분기(§7.3). 계산기 입력 폼도 모바일 단일 컬럼 기준으로 우선 설계.

### 2.4 면책 조항(공통)
- 실제 법적 효력이 있는 세무/노무 자문이 아닌 **참고용 모의 계산**임을 명시하되, **결과 하단뿐 아니라 입력 영역 진입 전(설명 영역 하단 등)에도 동일하게 노출**한다 — 특히 종합소득세·실업급여·육아휴직급여처럼 세무사·노무사 업무와 유사해 보이는 계산기는 무자격 상담으로 오인될 소지가 있어(§6.7) 결과만 보고 이탈하는 사용자도 고지를 보게 해야 함.

## 3. 개발 우선순위

`requirement.md` 하단에 정리된 근거—**① 카테고리 간 연관성으로 도구 간 이동(체류시간↑)**,
**② 검색 수요가 꾸준하고 금융/세금 광고 단가가 높음**, **③ 연초·최저임금 발표 시즌 트래픽 집중**—에 따라
1차 개발 범위는 **"1. 알바·직장인 관련" + "2. 프리랜서·사업자"** 로 확정한다.

- **Phase 1 (1차 아이템)**: 카테고리 1, 2 (급여/세금 도구 12종)
- **Phase 2**: 카테고리 3~6 (생활/주거, 육아/건강, 날짜/시간, 학생/수험생) — 검색 수요는 꾸준하나 광고 단가는 상대적으로 낮음, 트래픽 저변 확대 목적
- **Phase 3**: 카테고리 7 (텍스트·파일 도구) — 브라우저 내 처리형, 글로벌 트래픽 유입(비금전적 SEO 자산)
- **Phase 4**: 카테고리 8 (재미·바이럴형) — SNS 공유 유도, 신규 유입 채널 확보용(수익보다 트래픽 확산 목적)

## 4. 카테고리별 서브 메뉴 개발 근거

### 4.1 알바·직장인 관련 (Phase 1)

| 계산기 | 계산 근거(법령/공식) | 주요 입력 | 설정 파일화 대상 |
|---|---|---|---|
| 주휴수당 계산기 | 근로기준법 제55조·시행령 제30조(주휴일). 1주 소정근로시간 15시간 이상 + **해당 주 소정근로일 개근**이 조건. `주휴수당 = (1주 소정근로시간 ÷ 40) × 8 × 시급` (40시간 초과분은 8시간으로 고정, 실제근로시간이 아닌 **소정(약정)근로시간** 기준). 지각/조퇴는 무관하나 결근 시 미지급 | 시급, 주 소정근로시간, 개근 여부 | 최저시급 |
| 알바 월급 계산기 ✅구현 완료 | 근로기준법 제56조(연장·야간·휴일수당 가산). 연장·휴일 8시간 이내 50%, 야간(22~06시) 50%, 휴일 8시간 초과 100% 가산. **상시근로자 5인 미만 사업장은 가산수당 미적용**(근로기준법 시행령 별표1, 입력값으로 반영). 스코프는 **4대보험 공제 후 세후 실수령액까지**로 결정(사용자 확인) — 4대보험은 정확한 요율로 반영하되, 근로소득세는 "월급여 106만원(1인 가구) 미만이면 0원" 임계값만 반영하고 그 이상 구간은 정확한 세액을 계산하지 않고 국세청 간이세액표를 보라고 안내(방대한 조견표 전체를 반영하는 것은 별도 작업으로 분리). 주휴수당은 포함하지 않으며 별도 계산기로 안내 | 시급, 기본/연장/야간/휴일(8h 이내·초과) 근무시간, 사업장 규모(5인 이상 여부) | 최저시급, 가산율, 4대보험 요율(국민연금·건강보험·장기요양·고용보험), 소득세 0원 임계값 — 모두 `config/rates/labor.json`에 구현 완료 |
| 퇴사 시점 비교 계산기 | 근로자퇴직급여보장법(퇴직금 = 1년당 30일분 평균임금), 근로기준법 제60조(연차). 퇴사일에 따라 근속연수·연차 발생 여부가 달라짐을 비교 | 입사일, 예상 퇴사일(복수), 평균임금 | 없음(순수 계산) |
| 연차수당 계산기 | 근로기준법 제60조. 1년 미만: 1개월 개근당 1일, 1년 이상: 80% 이상 출근 시 15일, 3년차부터 2년마다 +1일(최대 25일) | 입사일, 기준일, 통상임금 | 없음(법정 기준은 고정, 회사 규정 예외는 안내문으로 처리) |
| 실업급여 모의 계산기 | 고용보험법(구직급여). `구직급여 = 이직 전 평균임금의 60% × 소정급여일수`, 상하한액 존재(단, 하한액은 최저임금 연동 파생값 — §7.2 참고). 소정급여일수는 연령·가입기간별 차등(120~270일) | 이직 전 평균임금, 나이, 고용보험 가입기간 | 상한액(고시 상수), 하한액(최저임금 기반 계산식), 소정급여일수 테이블(연도별 개정) |
| 육아휴직 급여 계산기 | 고용보험법 시행령. 최초 3개월: 통상임금 100%(상한 250만원 등, 연도별 개정), 4개월~종료: 통상임금 80%(상한 상이), 급여의 25%는 복직 6개월 후 사후지급 | 통상임금, 휴직 개월수 | 구간별 지급률/상한액(연도별 개정) |

### 4.2 프리랜서·사업자 (Phase 1)

| 계산기 | 계산 근거 | 주요 입력 | 설정 파일화 대상 |
|---|---|---|---|
| 3.3% 원천징수 역산 계산기 | 소득세법(사업소득 원천징수 3%) + 지방소득세(0.3%) = 3.3%. `세전 = 세후 ÷ 0.967`, `세후 = 세전 × 0.967` | 세전 또는 세후 금액 | 원천징수율(3.3%는 법정 고정이나 향후 변경 대비 설정화) |
| 부가세 계산기 | 부가가치세법(일반과세 10%). `공급가액 = 합계 ÷ 1.1`, `부가세 = 공급가액 × 0.1` | 공급가액 또는 합계금액 | 부가세율(간이과세자 등 예외 안내) |
| 종합소득세 예상 계산기(간이) ⚠️스코프 미정 | 소득세법 종합소득세 누진세율(6%~45%, 8단계 구간) + 기본공제. 프리랜서 단순 버전(경비율 적용 후 과세표준 산출). **공식 기준/단순경비율표는 업종코드 기준 수백 개 규모라 전체를 다 반영할지, 프리랜서에게 흔한 업종(1인 크리에이터, 강사, 디자이너, 배달라이더 등) 상위 다수만 우선 지원할지 결정 필요** | 연 매출/수입, 업종(제한된 목록 또는 직접 경비율 입력) | 누진세율표, 기본공제액, 지원 업종별 경비율(연도별 개정) |
| 배달 라이더 순수익 계산기 | 플랫폼 배달비 - (플랫폼 수수료 + 유류비/전기요금 + 보험료 + 사업소득세 3.3%) | 건당 배달비, 콜 수, 유류비, 보험료 | 플랫폼별 수수료율 |
| 스마트스토어·쿠팡 마진 계산기 | 판매가 - (원가 + 카테고리별 판매수수료 + 결제수수료 + 배송비) | 원가, 목표 마진율 또는 판매가, 카테고리 | 카테고리별 수수료율표(플랫폼별) |
| 해외직구 관세 계산기 | 관세법. 목록통관 면세한도(자가사용 기준, 미국발 별도 한도) 초과 시 관세+부가세(경우에 따라 개별소비세) 과세. `과세가격 = 물품가 × 환율`, 관세 = 과세가격 × 품목별 관세율, 부가세 = (과세가격+관세) × 10% | 구매금액(외화), 환율, 품목, 원산지 | 면세한도, 품목별 관세율, 환율(실시간 or 고시환율) |

> Phase 1 공통 사항: 최저임금·가산율·실업급여 상하한액 등 근로 관련 값은 `config/rates/labor.json`,
> 원천징수율·부가세율·소득세 누진표·관세 면세한도 등 세금 관련 값은 `config/rates/tax.json`으로 나누어 관리하고
> (§7.2), 각 계산기는 해당 도메인 파일의 값만 참조한다.

### 4.3 생활·주거 (Phase 2)

| 계산기 | 계산 근거 | 주요 입력 | 설정 파일화 대상 |
|---|---|---|---|
| 전기요금 계산기 | 한국전력 주택용 전기요금표(계절별 요금, 3단계 누진제). 사용량 구간별 상이한 kWh 단가 적용 | 사용량(kWh) 또는 가전 사용 패턴 | 계절별/구간별 요금표(개정 시마다 변경) |
| 전월세 전환율 계산기 ✅구현 완료 | 주택임대차보호법 제7조의2·시행령 제9조. `월세 = (전세금-보증금) × 전환율 ÷ 12`. 법정 상한 전환율 = **min(한국은행 기준금리+2%p, 연 10%)** — 2개 독립 출처로 교차검증 완료(2026-09-20). 기준금리는 자주 바뀌므로 하드코딩하지 않고 사용자가 직접 입력 | 전세보증금, 전환 후 보증금, 기준금리, 적용 전환율 | 없음(순수 계산식, 기준금리는 사용자 입력) |
| 중개수수료 계산기 | 공인중개사법 시행규칙, 지자체 조례상 거래금액 구간별 상한 요율(매매/전세/월세 별도) | 거래금액, 거래유형, 지역 | 구간별 상한요율표(지자체별 상이) |
| 대출 이자·상환 계산기 | 원리금균등: `월상환액 = 대출금×월이자율×(1+월이자율)^n ÷ ((1+월이자율)^n - 1)`, 원금균등: 매월 동일 원금 + 잔액 기준 이자 | 대출금, 연이자율, 상환기간 | 없음(순수 금융공식) |
| 이사 비용 견적 계산기 | 업계 평균 단가(평수×기본단가 + 층수/사다리차 가산 + 거리 가산)를 기준으로 한 추정치 제공 | 평수, 출발/도착 층수, 사다리차 여부, 이동거리 | 지역별/조건별 평균 단가표 |

### 4.4 육아·건강 (Phase 2)

| 계산기 | 계산 근거 | 주요 입력 |
|---|---|---|

| 출산 예정일 계산기 | Naegele's Rule: 마지막 생리 시작일 + 280일(40주) | 마지막 생리 시작일 |

### 4.7 텍스트·파일 도구 (Phase 3)

| 도구 | 개발 근거 | 처리 방식 |
|---|---|---|
| 글자수 세기 | 자기소개서 등 글자수 제한 대응 수요, 공백 포함/제외 카운트 | 클라이언트 JS (문자열 length 연산) |
| 이미지 압축·리사이즈·포맷 변환 | 서버 업로드 없이 브라우저에서 처리 → 개인정보 이슈 없음, 글로벌 트래픽 확보 용이 | Canvas API / WASM(예: `browser-image-compression`) |
| PDF 병합·분할 | 문서 작업 수요(글로벌 검색량 높음) | 클라이언트 라이브러리(예: `pdf-lib`) |
| 맞춤법 체크용 텍스트 정리 도구 | 국립국어원 맞춤법 규정 기반(또는 외부 맞춤법 API 연동 검토) | API 연동 또는 규칙 기반 |
| QR코드 생성기 | 정형화된 QR 인코딩 표준(ISO/IEC 18004) | 클라이언트 라이브러리(예: `qrcode`) |
| JSON·CSV 변환기 | 개발자 대상 트래픽, 데이터 포맷 표준 파싱/직렬화 | 클라이언트 JS 파싱 |

> 이 카테고리는 계산 "법적 근거"가 아닌 "포맷/표준 근거"이며, 전 도구를 브라우저 내 처리(No 업로드)로 구현해
> 무저장 원칙과 개인정보 리스크 최소화 요구사항을 동시에 만족.

### 4.8 재미·바이럴형 (Phase 4)

| 도구 | 개발 근거 |
|---|---|
| 이름 궁합·MBTI 궁합 테스트 | 확정적 근거 없는 엔터테인먼트 콘텐츠. SNS 공유를 통한 신규 유입 채널 확보가 목적(결과 공유 이미지/링크 기능 필요) |
| 랜덤 추첨기·사다리타기·룰렛 | 모임/회식 등 반복 사용 수요, 알고리즘은 단순 난수 생성(공정성 보장을 위한 `crypto.getRandomValues` 사용 권장) |
| 점심 메뉴 추천 룰렛 | 위와 동일한 랜덤 로직 재사용, 카테고리별 리스트만 상이 |
| 닉네임 생성기 | 규칙 기반 조합(형용사+명사 리스트 랜덤 조합) |
| 추천 조합 | 여러 도구를 조합 제안하는 랜딩/허브 페이지(직접 계산 없음, 내부 링크 구조 강화용) |

> Phase 4는 수익성보다 **공유 유도 → 신규 트래픽 확보**가 목적이므로, 결과 캡처/공유 버튼(OG 이미지 동적 생성 등)을
> 우선 구현하고 광고는 최소한으로 배치한다.

## 5. 개발 순서 요약

1. **공통 레이아웃/설정 시스템 구축**: 요율 설정 파일 스키마, 계산기 공통 템플릿(설명 영역+입력+결과+광고), 면책 문구 컴포넌트

## 7. 정보구조(IA)·URL 설계 (착수 전 확정 필요)

현재까지 계획에는 카테고리/계산기 **목록**만 있고, 이를 실제 사이트 구조로 어떻게 매핑할지는 정의되지 않았다.
개발 착수 전 아래 항목을 확정한다.

### 7.1 URL 구조(안, 슬러그 표기 규칙은 §7.4에서 최종 확정)
```
/                                    # 홈: 전체 카테고리 + 인기 도구 허브
/part-time                           # 대메뉴 랜딩(카테고리 소개 + 서브메뉴 목록, 콘텐츠 볼륨 확보용)
/part-time/weekly-holiday-pay        # 서브메뉴(개별 계산기) 페이지
/freelancer/withholding-tax-3-3
/privacy-policy                      # 개인정보처리방침 (6.2)
/terms                               # 이용약관
/about, /contact                     # 사이트 소개/문의 (애드센스 심사 요건)
```
- 카테고리 랜딩 페이지(`/part-time` 등)는 필수: 서브메뉴 링크 모음 + 카테고리 개요 설명으로 콘텐츠 깊이를 확보하고,
  계산기 간 내부링크(2.3의 "관련 도구 추천")의 허브 역할을 함.
- 위 예시는 §7.4의 (A) 완전 영문 의역 안을 적용한 것 — 최종 확정 전까지는 예시로만 참고.

### 7.2 설정 파일 스키마(확정: 도메인별 분리 파일)
- 요율/기준값은 **도메인별로 파일을 분리**하고, 파일 내부에서 연도를 키로 관리한다. 최저임금만 바뀌는 해에도 `labor.json` 하나만 수정하면 되고, 관리 포인트가 여러 군데로 흩어지지 않도록 도메인 수는 카테고리 8개가 아니라 **계산에 실제 요율이 필요한 도메인 단위**(labor, tax, realestate, electricity 등)로 묶는다.

```jsonc
// config/rates/labor.json — 근로/고용 관련(주휴수당, 알바월급, 연차, 실업급여, 육아휴직)
{
  "2026": {
    "minimumWage": { "hourly": 10320, "source": "https://www.minimumwage.go.kr" },
    "overtimePremium": { "extended": 0.5, "night": 0.5, "holidayUnder8h": 0.5, "holidayOver8h": 1.0 },
    "unemploymentBenefit": {
      "rate": 0.6,
      "dailyCap": 66000,
      "dailyFloorFormula": { "minWageRatio": 0.8, "hoursPerDay": 8 },
      "paymentDaysTable": [
        { "ageMax": 50, "insuredMonthsMax": 12, "days": 120 }
      ]
    },
    "parentalLeavePay": {
      "first3Months": { "rate": 1.0, "cap": 2500000 },
      "afterward": { "rate": 0.8, "cap": 1500000 },
      "deferredRate": 0.25
    }
  }
}

// config/rates/tax.json — 세금/사업자 관련(3.3%, 부가세, 종합소득세, 관세)
{
  "2026": {
    "withholdingTax": { "businessIncomeRate": 0.033 },
    "vat": { "rate": 0.1 },
    "incomeTaxBrackets": [
      { "upTo": 14000000, "rate": 0.06, "deduction": 0 }
    ],
    "customsDutyFreeLimit": { "default": 150, "usOrigin": 200, "currency": "USD" }
  }
}
```
- 값마다 `source` 필드로 1차 출처 URL을 함께 저장 — 페이지에 뿌릴 출처 링크(질문 2의 "보류" 결정과 별개로, 최소한 **내부 검증 근거로는 필수**) 및 향후 콘텐츠 표기 정책이 정해지면 그대로 노출 가능하도록 미리 구조에 반영.
- 연도 키를 객체로 감싸는 구조로 과거 연도 값도 같은 파일에 누적 → 연도 비교 기능(2.1) 구현이 쉬워짐.
- **파생값은 원시 상수로 저장하지 않는다**: 구직급여 하한액처럼 "최저임금 × 80% × 8시간"으로 계산되는 값을 독립된 숫자(`dailyFloor: 63104`)로 박아두면, 최저임금만 갱신하고 이 값을 깜빡했을 때 두 값이 서로 어긋나는 버그가 생긴다. 위 예시처럼 **계산식(`dailyFloorFormula`)만 저장하고 실제 값은 `minimumWage.hourly`를 참조해 런타임에 계산**한다. 반대로 구직급여 상한액(`dailyCap`)은 정부가 별도로 고시하는 독립값이므로 그대로 상수로 둔다 — 항목마다 "고시된 원시값인지 파생값인지"를 구분해서 스키마를 설계해야 한다.

### 7.2.1 콘텐츠 출처 표기 — 보류(미정)
- 계산 근거 설명 콘텐츠에 출처/작성자를 어떻게 노출할지는 **실제 콘텐츠 작성 시점에 결정**하기로 함(6.11 연동).
- 단, 설정 파일에는 위처럼 `source` 필드를 항상 채워 넣어, 표기 정책이 나중에 정해지더라도 소급 작업 없이 바로 노출할 수 있게 한다.

### 7.3 내비게이션 구조
- 8개 대메뉴 + 서브메뉴 다수 → 데스크톱은 메가메뉴, 모바일은 아코디언형 카테고리 목록으로 분기(§2.3에 공통 원칙으로 반영 완료).

### 7.4 URL 슬러그 로마자 표기 규칙 — 확정: (A) 완전 영문 의역
- 초안 단계에서 `/albar`(한글 로마자)와 `/freelancer`(영어 의역)가 섞여 있던 것을 발견해, Phase 3(글로벌 트래픽 목표, §6.8)와의 일관성을 고려해 **완전 영문 의역**으로 통일했다. §7.1의 예시(`/part-time/weekly-holiday-pay`, `/freelancer/withholding-tax-3-3`)가 최종 규칙이며, 앞으로 추가되는 모든 계산기 슬러그도 이 규칙을 따른다.
- (기각안) 한글 발음 로마자(`/albar/juhyu-sudang`) — 구현은 더 빠르지만 외국인·영어 사용자에게 의미가 전달되지 않아 채택하지 않음.

## 9. 출시 후 개선 이력 (2026-09-20 ~ 2026-09-23)

Phase 1~4 전체 구현 완료(§5.1) 및 GitHub Pages 실배포 이후, 실제 서비스 운영 중 발견된

### 9.1 디자인 리뉴얼 — "친절하고 귀여운 UI"
- 기존 UI가 딱딱한 느낌이라는 피드백에 따라, 실제 코드에 적용하기 전 저장소 루트에 정적
  프로토타입(`sample.html`, `sample-colors.html`, `sample-colors-v2.html` — 모두 git 미포함
  스크래치 파일)을 만들어 색상·레이아웃 여러 안을 시각적으로 검토한 뒤 최종안을 확정하는
  방식으로 진행.
- 최종안: 카테고리마다 칠해진 파스텔 카드(아이콘을 흰색 원형 배지에 담아 좌측 배치, 제목·
  설명은 좌측 정렬), 카드/버튼 모서리를 큼직하게 둥글림(`rounded-2xl`/`rounded-full`).
  오렌지색을 사이트 공통 브랜드 색상(홈 히어로, 헤더 로고, 버튼)으로 쓰고, 카테고리별로는
  8가지 파스텔 테마(알바·직장인=오렌지, 프리랜서·사업자=로즈, 생활·주거=스카이,
  육아·건강=에메랄드, 날짜·시간=앰버, 학생·수험생=인디고, 텍스트·파일=틸, 재미=바이올렛)를
  구분 적용. `site-config.ts`의 `CalculatorCategory.theme` 필드(cardBg/titleText/descText/
  badgeBg/badgeText/badgeHoverBg — Tailwind는 클래스명을 빌드 시점에 정적으로 스캔하므로
  런타임 문자열 조합이 아니라 완성된 클래스 문자열로 저장)로 관리.
- 처음에는 카테고리 **목록** 페이지(홈, 카테고리 랜딩)만 새 디자인이 적용되고 **상세**
  계산기 페이지(43개 전부)는 예전 스타일 그대로 방치돼 있던 것을 사용자가 지적해 발견 —
  모든 상세 페이지의 입력 카드·버튼·인풋에도 동일한 카테고리 색상 테마를 적용하고, `<h1>`
  제목에도 도구 아이콘을 붙여 통일감을 맞췄다(Python 스크립트로 47개 `page.tsx` + 42개
  `Calculator.tsx`를 기계적으로 일괄 치환).

### 9.2 헤더 내비게이션 버그 수정
- **드롭다운이 페이지 이동 후에도 열린 채로 남는 문제**: `Header`가 루트 레이아웃에 있어
  라우트가 바뀌어도 컴포넌트가 리마운트되지 않아 `<details open>` 상태가 이전 페이지 것
  그대로 유지됐음 → `<nav>`에 `key={pathname}`을 줘서 경로가 바뀔 때마다 서브트리를 통째로
  리마운트시켜 모든 드롭다운을 닫힌 상태로 되돌리는 방식으로 해결(커스텀 상태 관리 없이
  네이티브 `<details>`만으로 처리).
- **드롭다운이 열린 채 바깥을 클릭해도 안 닫히는 문제**: `document`에 클릭 이벤트 리스너를
  달아, nav 바깥을 클릭하면 열려 있는 `<details>`를 전부 닫도록 수정.
- **로고·메뉴·언어 전환 버튼 줄바꿈 문제(여러 차례 반복 수정)**: 영문 카테고리명이 한글보다
  훨씬 길어(예: "Freelancer & Self-Employed") 헤더 한 줄에 다 안 들어가던 문제를 카테고리명
  축약(예: "Freelance & Tax")으로 1차 완화. 이후에도 로고+언어전환 그룹과 메뉴(nav)가
  서로 다른 flex 아이템이라 총 너비가 넘치면 메뉴 전체가 통째로 다음 줄로 밀려나는 구조적
  문제가 남아있었음 — 로고를 `shrink-0`으로 고정하고 nav를 `flex-1 min-w-0`으로 바꿔 남은
  공간 안에서 메뉴 항목들이 개별적으로 줄바꿈되도록 구조를 바꿔 해결. 최종적으로 언어 전환
  버튼은 메뉴 끝이 아니라 **타이틀과 메뉴 사이**(로고 바로 옆)에 위치하도록 배치를 확정,
  한글판·영문판 모두 "타이틀 → 전환 버튼 → 메뉴" 순서로 한 줄에 표시됨을 실제 배포본
  스크린샷(헤드리스 Chrome)으로 확인.

### 9.5 모바일 헤더 반응형 정리 + 언어 자동 감지 + 도구 페이지 공유 버튼 (2026-09-23)

- **모바일 헤더 메뉴 정리**: 기존엔 카테고리 8개가 `<details>` 드롭다운으로 `flex-wrap`
  돼 있어, 좁은 화면에서 여러 줄로 줄바꿈되며 지저분해지고 드롭다운 패널(`w-64` 고정폭,
  `absolute left-0`)이 화면 우측 밖으로 넘칠 수 있었음(사용자가 실제 모바일 화면에서
  발견). `md` 이상에서는 기존 드롭다운 `nav`를 유지(`hidden md:flex`)하되 패널 기준을
  `right-0`으로 바꿔 넘침을 막고, `md` 미만에서는 햄버거 버튼(☰/✕) + 아코디언(`<details>`)
  패널로 된 전용 모바일 메뉴로 교체(`src/components/Header.tsx`). 모바일 메뉴 열림 상태는
  라우트가 바뀌면 자동으로 닫히는데, `useEffect` 안에서 `setState`를 호출하는 대신 렌더
  도중 이전 pathname과 비교해 갱신하는 패턴을 써서 lint의 `react-hooks/set-state-in-effect`
  경고를 피함.
- **브라우저 언어 기반 기본 언어 자동 전환**: 정적 내보내기(`output: export`)라 서버에서
  `Accept-Language`를 볼 수 없어 클라이언트에서 처리. 새 컴포넌트
  `src/components/LanguageRedirect.tsx`를 홈(`/`, `/en`) 페이지에만 넣어, 처음 방문했을
  때 한 번만 `navigator.language`를 확인해 한국어가 아니면 `/en`으로, 한국어면 `/`로
  리다이렉트. 리다이렉트 스코프(홈 전용 vs 전체 페이지)와 저장 방식(영구 vs 세션)을 사용자
  에게 직접 물어 "홈 전용, 세션당 1회"로 확정 — `sessionStorage`에 확인 여부를 남겨 같은
  탭에서는 다시 리다이렉트하지 않고, 탭을 새로 열면(새 세션) 다시 확인함.
- **도구 상세 페이지 공유 버튼**: "링크 복사 / 카카오톡·SNS 공유" 기능 요청에 대해,
  카카오 공식 SDK(공식 카카오톡 공유 카드)는 카카오 디벨로퍼스에서 발급받는 API 키가
  필요해 제외 — 대신 Web Share API(`navigator.share`)를 쓰기로 사용자와 합의. 지원
  브라우저(대부분의 모바일)에서는 "📤 공유하기" 버튼 하나가 OS 공유 시트를 띄우고, 카카오톡이
  설치돼 있으면 그 시트에서 바로 선택 가능. 미지원 환경(대부분의 데스크톱)에서는 "🔗 링크
  복사" + X·페이스북 공유 링크(둘 다 API 키 불필요, `intent`/`sharer.php` 공개 엔드포인트)로
  대체. `canShare`/`shareUrl`은 `useEffect`+`setState`가 아니라 `useSyncExternalStore`로
  읽어 서버 스냅샷을 항상 `false`/`""`로 고정, 하이드레이션 불일치 없이 클라이언트에서만
  실제 값으로 교체되게 함. 새 컴포넌트 `src/components/ShareButtons.tsx`를 43 KO + 42 EN
  도구 상세 페이지 전부의 `<h1>` 바로 아래에 기계적으로 삽입, 버튼 라벨은
  `content/ui/chrome.{ko,en}.json`의 `share.*` 키에서 로케일별로 조회.
  - **사후 검토**: 이후 사용자가 X/페이스북 대신 카카오톡·라인·인스타그램으로 바꿔달라고
    요청 → 각각의 실현 가능성을 확인해 안내(라인은 `social-plugins.line.me/lineit/share`
    공개 엔드포인트로 API 키 없이 가능하지만, 카카오톡은 API 키 없이는 버튼 자체가
    불가능하고 지금처럼 Web Share로만 커버 가능하며, 인스타그램은 애초에 웹 URL 공유
